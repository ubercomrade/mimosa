# GPU: 1 vs many и другие модели

## Протокол 1 vs many

Экспериментальный HIP-путь обрабатывает запрос один раз, далее по очереди
готовит наблюдаемый профиль каждой цели и четыре случайных профиля, сравнивает
их с запросом и обновляет отдельный GPU-счётчик для каждой пары. Случайные
профили переиспользуются по времени, массив K профилей не хранится. Входы:
один PWM из `examples/foxa2.meme`, 4 или 16 целей, полученных разными
переименованиями его букв, все длины 11; один миллион равномерных случайных
позиций, строки по 100, порог 3, сдвиги ±5, обе цепи, K=4, R-B и полная
группа. Цели связаны по происхождению: это инженерная нагрузка, а не
репрезентативная база мотивов. Случайные веса создаются на CPU до замеров.

Проверялось совпадение каждой Float32-оценки GPU со штатным CPU, а также
собственных GPU-счётчиков с CPU. Для 1×16 все 80 оценок и все 16 счётчиков
совпали; счётчики: `[0, 3, 4, 2, 2, 4, 1, 0, 2, 4, 0, 2, 3, 2, 1, 4]`.
Первый запрос–цель также побитово совпал с ранее измеренным 1×1 при тех же
данных, перестановках и параметрах. Это небольшая проверка воспроизводимости,
не доказательство для любых данных или реализации many×many.

| Работа | GPU, прогретые повторы, с | CPU, 8 потоков Numba, с |
| --- | --- | --- |
| 1×4, K=4 | 0.364, 0.362, 0.358 | 6.972, 6.514 |
| 1×16, K=4 | 1.387, 1.377, 1.383 | 25.638, 23.762 |

GPU-время включает передачу DNA и предварительно подготовленных весов, все
профили, J_w, счётчики и чтение результатов; контекст и буферы подготовлены до
замера. CPU-столбец использует один процесс, 8 потоков Numba, переиспользует
запрос и последовательно проходит цели. Это не единственная возможная CPU
конфигурация. Дополнительно для 1×16 проверена CPU-обработка восьмью joblib
процессами с одним потоком Numba на процесс, с общим запросом: первый запуск
8.296 с, второй с повторным использованием процессов 7.479 с; все 80 scores
совпали. На этом небольшом измерении сравнение прогретого повтора с медианой
GPU 1.383 с даёт около 5.4×; это не надёжная оценка для других входов. Время
формирования 16 наборов весов и записи файлов — 0.015 с, но CPU и GPU-таймеры
его не включают. Компиляция, чтение моделей и пиковая память не измерены.

GPU-профили целей пока обрабатываются последовательно, без пакетирования
моделей и межцелевого параллелизма. Этот прототип рассчитан на фиксированную
геометрию PWM, одинаковую длину строк, 1×many, K=4 и фиксированные файлы в
`/tmp`; не является API или готовым CLI. Оценивать по нему 408 целей, много
запросов или большой K без отдельных измерений нельзя.

## BaMM и остальные типы

Написан отдельный GPU-прототип кольцевого сканирования BaMM. Для одного
`examples/myog.ihbcp` длины 14 и миллиона позиций проверены обе цепи с N:

| Тип | Совпадение с CPU | GPU после прогрева, полное сканирование с передачами | CPU, 8 потоков, после прогрева |
| --- | --- | --- | --- |
| BaMM-0 | 2 млн Float32 значений побитово | 0.42–0.60 мс | 31–51 мс |
| BaMM-4 | 2 млн Float32 значений побитово | 1.07–1.20 мс | 48–60 мс |

После CPU-преобразования весов `relabel_model(..., seed=117)` BaMM-4 снова
совпал побитово на 2 млн оценок; GPU 1.02–1.03 мс, CPU 44–54 мс. Это только
сканирование, четыре прогона одного мотива, не полное время нормировки и
Monte Carlo и не доказательство корректности для всех моделей. Время GPU
включает передачу входов и выходов, но не инициализацию и не компиляцию. Первые
GPU вызовы занимали около 28–31 мс, начальная подготовка HIP — около 11–12 мс.

Для BaMM-4 таблица содержит 5⁵×14 Float32 весов, то есть 175 000 байт на
вариант. Такой объём не препятствует блочной обработке. Размер для порядка d
растёт как 5^(d+1)×длина; высокие порядки требуют отдельного ограничения и
измерения. Переименование BaMM должно согласовывать контексты и сейчас
выполняется на CPU существующей функцией; перенос генерации непосредственно на
GPU не проверен.

BaMM, Dimont и Slim используют в текущем MIMoSA одно rolling-ядро сканирования;
это делает перенос Dimont/Slim реалистичным, но их GPU результаты не проверены.
SiteGA также использует rolling-ядро для пар букв, с другой геометрией, и
нуждается в отдельной проверке. Произвольный пользовательский `MotifModel` или
`WindowModel` нельзя автоматически преобразовать в GPU-ядро: нужен явный GPU
интерфейс либо CPU fallback. Для смешанных коллекций последующие нормировка и
J_w общие, но распределение разных сканеров, передача профилей и согласованность
CPU/GPU пока не реализованы. Прототипы работают только на проверенной AMD GPU;
сборка и проверка NVIDIA отсутствуют.

Источники эксперимента: игнорируемые Git файлы `experiments/gpu/many_prepare.py`,
`many_parallel.py`, `many_cycle.cpp`, `bamm_prepare.py`, `bamm_scan.cpp`. Для
корректной сравнительной оценки нужны независимые разнообразные мотивы,
несколько размеров баз и K, повторения, лучшая CPU-конфигурация, замеры
пиковой памяти и полные циклы BaMM и смешанных коллекций.
