# Контекстные модели, кэш и варианты архитектуры

Дата: 17 ноября 2026. Это исследовательские прототипы, не перенос в production.
SiteGA не переносился. Предшествующие ограничения и протокол приведены в
`direct_mc_protocol.md` и `direct_mc_many_and_models.md`.

## Проверка сквозного вычисления

RX 9070 (`gfx1201`), HIP, Python 3.13, Numba 8 потоков; временная среда и
site-packages, описанные в `GPU_MONTE_CARLO_CONTEXT.md`. Вход — 10 000 строк
по 100 случайных символов с равной частотой A,C,G,T,N, 1 млн позиций на цепь;
порог 3, сдвиги ±5, четыре ориентации, K=4. Столь высокая доля N сделана для
инженерной проверки и не является биологически представительной.

Использовались реальные модели `examples/myog.ihbcp` порядка 0 и 4,
`tests/fixtures/stat_dimont-model-1.xml` и
`tests/fixtures/slim/example-model-1.xml`. В одном тесте запрос и цель
совпадали. В другом один запрос сравнивался с четырьмя целями, полученными из
той же модели переименованием; это не независимая коллекция. Первая реплика —
тождественное преобразование, чтобы гарантировать ничью; остальные две из
полной группы и одна из GC-подгруппы, с весами, подготовленными на CPU.
Это **смешанный набор для проверки**, не выборка из одного статистического
нуля и не оценка p-value. Обе реализации получали одни и те же веса.

CPU: `prepare_profile` с `circular=True`, затем `compare`; GPU: сканирование
обеих цепей, точная ранговая нормировка, порог, все сдвиги и ориентации,
последовательная редукция строк и сравнение с наблюдаемым J_w. Все 20 Float32
J_w в каждом 1×4 опыте совпали побитово, в том числе принудительные ничьи.
Первые пять оценок также совпали с отдельным 1×1.

| Модель | Порядок, длина | CPU/GPU counts в 1×4 | GPU 1×4, прогретые 3 прогона, с |
|---|---:|---|---|
| BaMM | 0, 14 | `[1, 2, 2, 3]` | 0.330, 0.324, 0.320 |
| BaMM | 4, 14 | `[1, 2, 2, 1]` | 0.335, 0.333, 0.332 |
| Dimont | 3, 5 | `[1, 4, 1, 4]` | 0.326, 0.324, 0.321 |
| Slim | 5, 15 | `[1, 1, 3, 2]` | 0.335, 0.335, 0.329 |

Время GPU включает загрузку последовательности и заранее рассчитанных весов,
построение и сравнение профилей и чтение J_w/counts; инициализация и аллокация
заняли дополнительно 0.012–0.013 с; первые проходы — 0.458–0.477 с.
Компиляция и подготовка весов не измерены. CPU-времена 5.90–7.53 с получены
по одному последовательному проходу с 8 Numba-потоками и не являются честной
оценкой максимальной производительности CPU; конкурентное выполнение тестов
влияло на первый набор 1×1. Цифры не экстраполировать на реальную базу.

CPU-тесты `tests/test_randomization.py` дополнительно проверяют соответствие
native/generic явному покомпонентному перекодированию входа, включая короткие
строки, N, обе цепи и circular, для этих моделей. GPU сейчас принимает уже
преобразованные CPU веса, поэтому это **не проверка GPU-рандомизации**.

## Временное использование профиля против пересчёта

`cache_probe.cpp` измеряет Slim порядка 5, длины 15, на том же входе: профиль
двух цепей — 8 000 000 байт. Сравнивается один и тот же уже нормированный
Float32 профиль. Измерения wall-clock, операции синхронизированы; 11 прогретых
повторов после первого:

| Операция | Диапазон, мс |
|---|---:|
| Повторное сканирование + копия + полная сортировка + нормировка | 2.429–2.644 |
| VRAM→VRAM, включая синхронизацию | 0.039–0.042 |
| RAM pageable→VRAM | 0.162–0.171 |
| VRAM→RAM pageable | 0.161–0.175 |
| RAM pinned→VRAM / VRAM→RAM pinned | 0.150–0.162 / 0.155–0.165 |

Повторное использование профиля прямо в VRAM не требует даже VRAM→VRAM копии.
Измеренный полный обмен pageable туда и обратно примерно 0.32–0.35 мс, один
возврат RAM→VRAM около 0.16–0.17 мс, против 2.43–2.64 мс пересчёта.
Это не дисковый тест; RAM уже выделена, данные, последовательность и веса
находятся в памяти, проверки корректности кэша, дополнительные аллокации и
создание весов в замерах отсутствуют. Ядро гипотезы подтверждено для данного
случая, но не для всех моделей, размеров и нагрузок.

Предварительная стратегия: хранить нужный блок нормированных профилей в VRAM,
пока он используется; при нехватке места сравнить блокирование и выгрузку в
RAM с пересчётом. Постоянный диск сделать необязательным и отдельно замерить
включая сериализацию, проверки, cold/warm page cache и передачу на GPU.
При 1 млн позиций на цепь 408 плотных профилей занимают 3.264 GB только под
Float32 оценки, без offsets, anchors, сортировки, scratch, моделей и runtime.
Приблизить доступный размер блока можно только после измерения реального пика.
В отдельном микроопыте `hipMemGetInfo` до и после показал уменьшение свободной
памяти примерно на 191 MB при 33.94 MB явных device-буферов: это разность
снимков, **не пик VRAM**, и она зависит от контекста и аллокатора.

## Архитектура

Предварительно предпочтителен существующий Python API и CPU fallback, с
опциональным нативным вычислительным backend: C++ и HIP-ядра, отдельные сборки
для AMD и NVIDIA; адаптеры для их библиотек сортировки и отдельные CI-проверки.
Декодирование моделей, выбор backend, R-B контракт и формирование результата
остаются общими. Не переписывать существующий CPU путь только ради этого.
Предлагать эту схему как гипотезу до проверки NVIDIA и дистрибуции, а не как
готовое решение. CPU-only wheel должен работать без GPU runtime; матрицу
wheels/OS/драйверов и способ связывания зависимостей требуется проверить.

JAX стоит рассмотреть отдельным ограниченным прототипом, но не выбирать вместо
HIP по обещанию переносимости: JAX ещё не установлен и не измерен здесь.
Согласно [установке JAX](https://docs.jax.dev/en/latest/installation.html),
бинарные зависимости и GPU-плагины платформенно специфичны, поддержка AMD
зависит от ROCm и версии плагина, NVIDIA использует CUDA, а поддержка OS
различается. Проверить конкретные wheel, `gfx1201`, версии и размеры установки.
У JAX по умолчанию отключён Float64; включение x64 необходимо для данного
J_w, но само по себе не гарантирует порядок сумм, одинаковые `log10`, сравнение
ничьих и побитовую идентичность. Измерение должно синхронизировать устройство
(`block_until_ready`), отдельно учитывать JIT и все передачи. Возможны
специализированные ядра, что уменьшит предполагаемое преимущество единого
высокоуровневого кода. HIP аналогично не обещает автоматически одинаковые
результаты CPU/AMD/NVIDIA: нужны зафиксированные семантика и acceptance tests.
Документация: [HIP compilation](https://rocm.docs.amd.com/projects/HIP/en/latest/understand/compilers.html),
[JAX X64](https://docs.jax.dev/en/latest/101/default_dtypes.html),
[JAX profiling](https://docs.jax.dev/en/latest/201/profiling.html).

## Открытые пункты

- Динамические и неодинаковые длины строк, короткие и пустые строки, широкий
  набор весов/порядков, граничные условия и близкие ничьи на GPU.
- Смешанные коллекции, 1×many и many×many с общим планировщиком, 408×408,
  репрезентативные модели и реальный FASTA, пик VRAM/RAM, времена для разных K.
- Независимые полные/GC Monte Carlo реплики, GPU преобразование контекстов,
  детерминизм seed/порядка базы, NVIDIA и CPU fallback.
- Замеры JAX и честное сравнение холодного старта, упаковки и всех backend.

Экспериментальные исходники `experiments/gpu/context_cycle.cpp`,
`context_check.py`, `cache_probe.cpp` намеренно находятся в игнорируемом Git
каталоге. Они используют фиксированные файлы `/tmp/mimosa_many_*.bin`, и их
нельзя запускать параллельно. Компиляция: `hipcc -O3 --offload-arch=gfx1201
experiments/gpu/context_cycle.cpp -o /tmp/opencode/context_cycle`, затем
`context_check.py --many` в описанной временной среде. После этого аналогично
компилировать и запускать `cache_probe.cpp`; последний ожидает Slim-веса,
записанные последним проходом `context_check.py`.

Проверки: `python -m pytest -q tests` — 410 passed; `python -m ruff check .` —
успешно, обе команды в описанной временной среде. Запуск pytest из корня
завершился на сборе тестов из игнорируемого `experiments/jaspar_bpnet`
(отсутствуют `/tmp/mimosa-jaspar-dl/planted/rings.npy` и `h5py`).
Это не эквивалент успешного полного CI с `uv sync --locked --group dev`.
