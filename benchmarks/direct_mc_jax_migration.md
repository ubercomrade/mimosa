# Переход MIMoSA на Python/JAX: численная совместимость и CPU

Продолжение `direct_mc_jax_assessment.md`. Целевая архитектура — сохранить по
возможности Python API и заменить Numba на JAX, включая CPU; изменения API для
direct Monte Carlo проектируются отдельно. На текущем этапе production-код не
менялся и Numba не удалялся.

## Порядок редукции и близкая ничья

`experiments/gpu/jax_reduction_probe.py` сравнивает один сдвиг и одну
ориентацию для 10 000 синтетических строк по 100 Float32 значений, порог 3.
Это не полноценное 1×1 сравнение со всеми ориентациями и не модельный
Monte Carlo. CPU-эталон — `_jaccard_orientation` MIMoSA с CSR anchors.

Проверены JAX-варианты:

* `dense`: параллельное суммирование Float64 по плотной маске объединения;
* `ordered`: последовательно обходит позиции query, затем target-only в каждой
  строке и затем суммирует строки по порядку, воспроизводя порядок CPU.

В обычном наборе искусственных экспоненциальных значений и его варианте,
отличающемся на один ULP одной позиции, CPU и оба варианта JAX на GPU и CPU
дали одинаковые Float64 и Float32 оценки. Исходный и изменённый Float64
результаты различались примерно на 7.6e-14, но округлялись к одной Float32
оценке: в текущем MIMoSA это ничья. Отдельно проверена точная копия.

В дополнение искусственно заданы 1 млн активных позиций, веса около 3 и малые
значения около `2.17e-7`. Это не проверка достижимости именно такого профиля
ранговой нормировкой. На RX 9070 параллельная редукция действительно дала
другую Float64 оценку: `0.4838710176513348` против CPU
`0.4838710176513297`, разница примерно `5.05e-15`. Последовательный JAX
совпал с CPU на этом примере; после преобразования в Float32 оба совпали.
Ни смены Float32 решения о ничьей, ни универсальной идентичности не доказано.
Тестируемый случай показывает, почему сравнения близко к границе округления
нужны до смены численного контракта.

Прогретые GPU вызовы `dense` занимали примерно 0.14–0.22 мс на один сдвиг и
ориентацию, `ordered` — 88–101 мс. Последний многократно запускает
последовательный цикл строк; это наивная реализация и **не нижняя граница**
стоимости точного порядка. Начальная JIT-компиляция не входит. Сопоставлять эти
цифры с полным сравнением всех 44 вариантов нельзя.

На JAX CPU в обычном случае тот же `dense` занимал примерно 1.1–3.1 мс,
`ordered` — 5.5–7.3 мс после прогрева. Это сравнение отдельных алгоритмов,
не полный CPU benchmark и не достаточное основание для удаления Numba.

## Полный фиксированный прототип на JAX CPU

На том же входе Dimont-3 и тех же весах, что в предыдущем отчёте, запуск
`experiments/gpu/jax_probe.py` с `JAX_PLATFORMS=cpu` также побитово совпал
по scan, нормированному профилю запроса и 20 Float32 J_w с эталоном;
counts `[1, 4, 1, 4]`. Времена полного 1×4 K=4 JAX CPU после первого
выполнения — 14.74, 14.93 и 14.47 с; нормализация одного профиля
0.59–0.61 с после прогрева, scan 13–19 мс, одно сравнение 77–92 мс.
Первое выполнение отдельных стадий, включая JIT, — 0.28, 0.68 и 0.22 с.

Ранее CPU MIMoSA/Numba выполнил сопоставимый, но не идентичный Dimont опыт
примерно за 5.6 с одним прогоном. Это не честный benchmark по потокам,
алгоритмам и накладным расходам: JAX dense и CPU sparse имеют разную работу,
а benchmark CPU включает подготовку объектов и повторное сканирование для
проверки; JAX включает копирование массивов и компиляцию части обвязки.
Текущая JAX CPU нормировка использует sort и `searchsorted` для каждого
элемента. Вывод: **CPU fallback работает на примере, но производительность
полного отказа от Numba пока не подтверждена**. Нужен оптимизированный
сопоставимый тест с разным числом потоков и реальными профилями.

## План перехода

1. Зафиксировать численный контракт Float32 итогового J_w, tie `>=`, группы
   перестановок, seed по идентичности модели/реплики и независимость от режима
   и состава базы. Протокол R-B остаётся общим для всех backend.
2. Исследовать быстрый точный или детерминированный вариант JAX редукции:
   сжатие anchors, контролируемый порядок, группирование, возможно точные
   аккумуляторы. Сначала собрать контрпримеры для Float32/counts и измерить
   стоимость, а не менять незаметно критерий равенства.
3. Написать общий JAX backend сканирования PWM/BaMM/Dimont/Slim, нормировки,
   выравнивания и randomization, начиная с CPU-генерации перестановок.
   Обработать ragged данные, N, short/empty rows, иной background и равные
   scores. SiteGA не входит в GPU-перенос; судьбу существующего SiteGA API
   согласовать отдельно до удаления Numba.
4. Сохранить существующие форматы, публичные модели, идентичность результата и
   прогнать набор тестов на JAX CPU/AMD/NVIDIA. Пользовательские модели
   нуждаются в отдельном контракте — произвольный Python callback нельзя
   автоматически компилировать JAX.
5. Выполнить 1×1, 1×many и many×many, K, 408×408 и профили памяти в
   эквивалентных условиях; доказать отсутствие зависимости пары от соседей.
   Только после корректности и достаточной CPU-производительности планировать
   окончательное удаление Numba и переход lockfile/релизной матрицы.

## Повторение

В изолированную JAX-среду из предыдущего отчёта дополнительно установлены
`numpy==2.4.6`, `numba==0.66.0`, `joblib`; Numba здесь используется только как
эталон. Никакие зависимости проекта не менялись. Команды:

```bash
LD_LIBRARY_PATH=/opt/rocm/lib/rocm_sysdeps/lib LLVM_PATH=/opt/rocm/llvm \
XLA_PYTHON_CLIENT_PREALLOCATE=false JAX_PLATFORMS=rocm \
PYTHONPATH="$PWD/src:$PWD/.venv/lib/python3.13/site-packages" \
NUMBA_CACHE_DIR=/tmp/mimosa-numba-cache NUMBA_NUM_THREADS=8 \
/tmp/opencode/mimosa-jax-env/bin/python experiments/gpu/jax_reduction_probe.py
```

Добавить `MIMOSA_ADVERSARIAL=1` для искусственной смеси масштабов; заменить
`JAX_PLATFORMS=rocm` на `cpu` для CPU. Для полного Dimont CPU опыта сначала
подготовить входы командой `context_check.py --many --case dimont`, как в
предыдущем отчёте, а затем запустить `jax_probe.py` с `MIMOSA_WIDTH=5`,
`MIMOSA_ORDER=3`, `JAX_PLATFORMS=cpu`. `experiments/` игнорируется Git.
